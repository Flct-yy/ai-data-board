## 1. 设计目标

认证系统需要满足以下需求：

1. **邮箱密码登录 / 注册**：用户可通过邮箱和密码创建账号、登录。
2. **登录态持久化**：刷新页面后仍保持登录。
3. **服务端与客户端都能感知登录态**：Server Component 能 SSR 出用户信息，Client Component 也能读取。
4. **Token 自动刷新**：access token 过期时自动用 refresh token 续期。
5. **登出干净**：清除 cookie，跳转到登录页。
6. **可扩展**：未来加 OAuth、Magic Link、密码重置时不用重构。

**核心原则：认证逻辑分层——浏览器端、服务端、中间件各司其职，Cookie 在它们之间正确传递。**

## 4. 为什么需要三种 Supabase Client

Supabase Auth 在不同环境下的 Cookie 读写方式不同：

| 环境              | Cookie 来源                    | 可写性   | Client                |
| ----------------- | ------------------------------ | -------- | --------------------- |
| 浏览器            | `document.cookie`              | 可读写   | `createBrowserClient` |
| Server Component  | `next/headers` 的 `cookies()`  | **只读** | `createServerClient`  |
| Route Handler     | `next/headers` 的 `cookies()`  | 可读写   | `createServerClient`  |
| Middleware / Edge | `NextRequest` / `NextResponse` | 可读写   | `createServerClient`  |

**因此项目拆出三个 `createClient`：**

- `utils/supabase/client.ts`：浏览器端（登录页表单用）。
- `utils/supabase/server.ts`：Server Component / Route Handler 用（登录页检查、登出 API）。
- `utils/supabase/middleware.ts`：Middleware 专用（token 刷新）。

**认证系统的关键约定：**

> **登录必须在浏览器端完成**（`client.ts`），因为 `@supabase/ssr` 的 `createBrowserClient` 会自动把 session 写入 cookie。
>
> **登出必须在服务端完成**（`server.ts`），因为需要清除 HttpOnly cookie。
>
> **Token 刷新由 Middleware 完成**（`middleware.ts`），每次请求触发。

## 5. 源码逐文件解析

### 5.1 `login/page.tsx`（登录页）

```tsx
import { redirect } from "next/navigation";
import { cookies } from "next/headers";
import { createClient } from "@/utils/supabase/server";
import { LoginForm } from "@/components/auth/login-form";

export default async function LoginPage() {
  // 已登录用户直接跳回首页
  const cookieStore = await cookies();
  const supabase = createClient(cookieStore);
  const {
    data: { user },
  } = await supabase.auth.getUser();

  if (user) {
    redirect("/");
  }

  return (
    <main className="mx-auto flex min-h-screen max-w-sm flex-col justify-center px-4">
      <header className="mb-8 text-center">
        <h1 className="text-2xl font-bold tracking-tight">登录</h1>
        <p className="mt-1 text-sm text-gray-500">登录后即可上传 CSV 并使用 AI 分析</p>
      </header>

      <LoginForm />
    </main>
  );
}
```

**逻辑解析：**

1. **Server Component**：`async function`，无 `"use client"`。
2. **用 `server.ts` 的 `createClient`**：传 `cookieStore`，读服务端 cookie。
3. **`getUser()` 检查登录态**：
   - 已登录 → `redirect("/")`，避免重复登录。
   - 未登录 → 渲染 `<LoginForm>`。
4. **`LoginForm` 是 Client Component**：表单交互需要 `useState` 和事件处理。

**为什么不在 Server Component 里直接处理登录？**

- 登录需要写 cookie，而 **Server Component 的 `cookies()` 是只读的**，写会抛错。
- 登录必须在浏览器端或 Route Handler 完成。
- 这里选择浏览器端，因为 `createBrowserClient` 会自动同步 cookie，代码更少。

**`redirect("/")` 的行为：**

- Next.js 的 `redirect()` 抛出一个特殊错误，中断当前渲染，返回 307 重定向。
- 必须在 `return` 之外调用，且不能在 `try/catch` 里（会被吞掉）。

### 5.2 `login-form.tsx`（登录表单）

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";
import { createClient } from "@/utils/supabase/client";

type Mode = "signin" | "signup";

export function LoginForm() {
  const router = useRouter();
  const [mode, setMode] = useState<Mode>("signin");
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState("");
  const [notice, setNotice] = useState("");
  const [loading, setLoading] = useState(false);

  const supabase = createClient();

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    setLoading(true);
    setError("");
    setNotice("");

    if (mode === "signin") {
      const { error } = await supabase.auth.signInWithPassword({
        email,
        password,
      });

      if (error) {
        setError(error.message);
        setLoading(false);
        return;
      }

      router.push("/");
      router.refresh();
      return;
    }

    // signup
    const { data, error } = await supabase.auth.signUp({ email, password });

    if (error) {
      setError(error.message);
      setLoading(false);
      return;
    }

    if (!data.session) {
      setNotice("注册成功，请检查邮箱确认后再登录。");
      setMode("signin");
      setLoading(false);
      return;
    }

    router.push("/");
    router.refresh();
  };

  // ... JSX 表单
}
```

**关键设计：**

**A. `"use client"` 指令**

- 声明为 Client Component。
- 因为要用 `useState`、`useRouter`、事件处理。

**B. 用 `client.ts` 的 `createClient`**

```ts
import { createClient } from "@/utils/supabase/client";
const supabase = createClient();
```

- **必须是浏览器端 client**（`createBrowserClient`）。
- 它内部用 `document.cookie` 管理 session。
- 登录成功后自动写入 cookie，无需手动处理。

**C. 双模式：`signin` / `signup`**

- 一个组件处理登录和注册。
- `mode` state 切换 UI 和调用逻辑。

**D. `router.push("/") + router.refresh()`**

- `push`：跳转到首页。
- `refresh`：**强制 Server Component 重新渲染**，读取新 cookie。
- **缺了 `refresh` 会导致首页仍显示未登录状态。**

**E. 邮箱确认处理**

```ts
if (!data.session) {
  setNotice("注册成功，请检查邮箱确认后再登录。");
  setMode("signin");
  return;
}
```

- Supabase 项目开启 "Confirm email" 时，`signUp` 返回的 `session` 为 `null`。
- 此时提示用户去邮箱确认，切换到登录模式。
- 若关闭了邮箱确认，`session` 有值，直接登录成功。

**F. 错误处理**

- `error.message` 是 Supabase 返回的原始错误（如 `Invalid login credentials`）。
- 直接展示给用户，简单直接。

**G. `loading` 状态**

- 提交时禁用按钮，防止重复提交。
- 按钮文案随 `mode` 变化。

### 5.3 `auth/signout/route.ts`（登出 API）

```ts
import { NextResponse } from "next/server";
import { cookies } from "next/headers";
import { createClient } from "@/utils/supabase/server";

export async function POST(req: Request) {
  try {
    const cookieStore = await cookies();
    const supabase = createClient(cookieStore);
    await supabase.auth.signOut();
  } catch (err) {
    console.error("[signout] error:", err);
  }

  return NextResponse.redirect(new URL("/login", req.url));
}
```

**逻辑解析：**

1. **导出 `POST`**：Next.js 只识别具名导出的 HTTP 方法。
2. **`await cookies()`**：Next.js 15 起 `cookies()` 是异步的。
3. **`createClient(cookieStore)`**：用 `server.ts` 的 client，能写 cookie。
4. **`signOut()`**：清除 session，**服务端会 `Set-Cookie` 把 token 置空**。
5. **`try/catch`**：即使 signOut 失败也继续重定向，避免用户卡住。
6. **`new URL("/login", req.url)`**：用绝对 URL 重定向，`req.url` 自动带 origin。

**为什么用 `POST` 而不是 `GET`：**

- 登出是**状态改变**操作。
- `GET` 会被浏览器预取、爬虫触发、链接预加载触发 → 意外登出。
- HTML 表单默认 `GET`，必须显式 `method="post"`。

**为什么返回 `NextResponse.redirect` 而不是 JSON：**

- 直接服务端重定向，浏览器自动跟随。
- 无需前端 JS 处理，`<form>` 原生提交即可。
- 更少的客户端代码，更可靠。

### 5.4 `user-menu.tsx`（用户菜单）

```tsx
"use client";

import { useEffect, useState } from "react";
import { createClient } from "@/utils/supabase/client";
import type { User } from "@supabase/supabase-js";

export function UserMenu() {
  const [user, setUser] = useState<User | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    const supabase = createClient();

    supabase.auth.getUser().then(({ data }) => {
      setUser(data.user);
      setLoading(false);
    });

    const {
      data: { subscription },
    } = supabase.auth.onAuthStateChange((_event, session) => {
      setUser(session?.user ?? null);
    });

    return () => subscription.unsubscribe();
  }, []);

  if (loading) return null;

  if (!user) {
    return (
      <a href="/login" className="text-sm text-brand-600 hover:underline">
        登录
      </a>
    );
  }

  return (
    <div className="flex items-center gap-3 text-sm">
      <span className="text-gray-500">{user.email}</span>
      <form action="/auth/signout" method="post">
        <button type="submit" className="text-gray-500 hover:text-brand-600">
          登出
        </button>
      </form>
    </div>
  );
}
```

**关键设计：**

**A. 初始加载 + 监听变化**

```ts
supabase.auth.getUser().then(...)          // 初始拉取
supabase.auth.onAuthStateChange(...)       // 订阅变化
```

- `getUser`：首次加载时拉取当前用户。
- `onAuthStateChange`：登录、登出、token 刷新时回调。
- 两者配合，UI 状态始终同步。

**B. 清理订阅**

```ts
return () => subscription.unsubscribe();
```

- `useEffect` 卸载时取消订阅，防止内存泄漏。

**C. 未登录 / 已登录分支**

- 未登录：显示"登录"链接。
- 已登录：显示邮箱 + 登出按钮。

**D. 用原生 `<form>` 提交登出**

```tsx
<form action="/auth/signout" method="post">
```

- **`method="post"` 必须有**——否则浏览器用 GET 导航，404。
- `action="/auth/signout"` 必须与 `route.ts` 所在路径一致。
- 原生表单提交，无需 JS。

**E. `loading` 时返回 `null`**

- 避免闪烁（先显示"登录"再切成邮箱）。
- 也可以返回骨架屏。

## 6. 认证流程详解

### 6.1 首次登录

```
1. 用户访问 /login
2. page.tsx 检查 getUser() → null
3. 渲染 <LoginForm>
4. 用户输入邮箱密码，点"登录"
5. signInWithPassword 调 Supabase Auth API
6. Supabase 返回 access_token + refresh_token
7. createBrowserClient 自动写入 cookie：
   sb-<project>-auth-token = <session>
8. router.push("/") + router.refresh()
9. 首页 Server Component 读 cookie → getUser() → 识别用户
```

### 6.2 后续请求

```
1. 用户请求 /dashboard
2. middleware.ts 拦截
3. createClient(request) + getUser() → 触发 token 刷新
4. Supabase 检查 refresh_token，若 access_token 过期：
   - 用 refresh_token 换新 access_token
   - setAll 写新 cookie 到 request 和 response
5. 返回 response，携带 Set-Cookie
6. Server Component / API 读 cookie → 识别用户
```

### 6.3 Token 刷新

- **触发点**：`middleware.ts` 里的 `getUser()`。
- **必要条件**：每次请求都经过 Middleware。
- **结果**：access token 自动续期，用户无感知。
- **失败时**：refresh_token 也过期 → `getUser()` 返回 null → RLS 拒绝 → 前端可重定向到 `/login`。

### 6.4 登出

```
1. 用户点"登出"
2. <form method="post"> 提交到 /auth/signout
3. route.ts 执行 signOut()
4. Supabase 清服务端 session
5. 返回 Set-Cookie 把 token 置空
6. NextResponse.redirect("/login")
7. 浏览器跳转 /login，cookie 已清
```

## 7. Cookie 与 Session 的传递

### 7.1 Cookie 名称

Supabase Auth 的 cookie 名格式：

```
sb-<project-ref>-auth-token
sb-<project-ref>-auth-token-code-verifier
```

`<project-ref>` 是 Supabase URL 里的子域，例如 `https://abcdefg.supabase.co` 的 ref 是 `abcdefg`。

### 7.2 Cookie 内容

- `auth-token`：序列化的 session（含 access_token、refresh_token、user）。
- 通常被 `@supabase/ssr` 加密或分段存储。
- 有时会分成多段（`.0`、`.1`），因为单 cookie 有 4KB 限制。

### 7.3 Cookie 属性

| 属性       | 值                          | 说明                                              |
| ---------- | --------------------------- | ------------------------------------------------- |
| `HttpOnly` | 视配置                      | Supabase SSR 默认允许 JS 读（因为浏览器端也要用） |
| `Secure`   | 生产环境 true               | localhost 例外，允许 HTTP                         |
| `SameSite` | `Lax`                       | 防 CSRF                                           |
| `Path`     | `/`                         | 全站共享                                          |
| `Max-Age`  | 与 refresh_token 有效期一致 | 默认 30 天                                        |

### 7.4 三段式传递

```
浏览器 → 请求带 Cookie → Middleware 读到 → 传给 Server Component
                                ↓
                        刷新后写新 Cookie
                                ↓
Server Component → 响应带 Set-Cookie → 浏览器更新
```

**关键：`middleware.ts` 必须把刷新后的 cookie 写回响应**，否则浏览器 cookie 一直是旧的。

## 8. 路由保护

**当前 `middleware.ts` 的保护逻辑是注释掉的：**

```ts
// if (!user && request.nextUrl.pathname.startsWith('/dashboard')) {
//   const url = request.nextUrl.clone();
//   url.pathname = '/login';
//   return NextResponse.redirect(url);
// }
```

**要启用，建议这样写：**

```ts
export async function middleware(request: NextRequest) {
  const supabaseClient = createClient(request);
  const {
    data: { user },
  } = await supabaseClient.supabase.auth.getUser();

  const { pathname } = request.nextUrl;

  // 需要登录的路径前缀
  const protectedPrefixes = ["/analyze", "/history"];

  // 认证相关路径（不重定向）
  const authPrefixes = ["/login", "/auth"];

  if (
    !user &&
    protectedPrefixes.some(p => pathname.startsWith(p)) &&
    !authPrefixes.some(p => pathname.startsWith(p))
  ) {
    const url = request.nextUrl.clone();
    url.pathname = "/login";
    return NextResponse.redirect(url);
  }

  return supabaseClient.response;
}
```

**要点：**

1. **保护列表**：`/analyze`、`/history` 等需要登录的路径。
2. **排除认证路径**：`/login`、`/auth/*` 不要触发重定向，否则死循环。
3. **放行其他**：首页 `/` 允许匿名访问。

**为什么在 Middleware 而不在页面里做：**

- Middleware 在 Edge 跑，**先于**页面渲染。
- 未登录时直接 302，不浪费 Server Component 的渲染资源。
- 页面级检查需要每个页面写一遍，重复。

```
    chat/
    upload/
  utils/
    supabase/
      client.ts
      server.ts
      middleware.ts
```

**约定：**

| 前缀                | 用途         | 例子                              |
| ------------------- | ------------ | --------------------------------- |
| `app/api/*`         | 数据接口     | `/api/sessions`、`/api/analyze`   |
| `app/auth/*`        | 认证流程     | `/auth/signout`、`/auth/callback` |
| `app/login/*`       | 登录页面     | `/login`                          |
| `components/auth/*` | 认证相关组件 | `LoginForm`、`UserMenu`           |

**为什么分开：**

- **语义清晰**：看路径就知道是数据还是认证。
- **中间件易写**：`pathname.startsWith('/auth')` 排除认证路径。
- **对齐官方示例**：Supabase 官方 Next.js 示例用同样的约定。

**注意：`/auth/signout` 和 `/api/signout` 在技术上等价**——都是 Route Handler。分开纯粹是约定，不是 Next.js 强制。

## 11. 常见问题与排查

### 11.1 登录报 `Invalid login credentials`

**原因：** 用户不存在、密码错、或邮箱未确认。

**排查：**

1. Dashboard → Authentication → Users 里有没有这个邮箱。
2. 密码是否正确（区分大小写）。
3. 邮箱是否已确认（若开启 Confirm email）。

**修复：**

- 用户不存在 → 走注册。
- 密码错 → Dashboard 重置密码，或删掉重建。
- 邮箱未确认 → 关闭 Confirm email，删掉用户重新注册。

### 11.2 登录成功但 API 返回 401

**原因：** Cookie 没写入，或 API 用的 client 不对。

**排查：**

1. DevTools → Application → Cookies 看有没有 `sb-*-auth-token`。
2. API 是否用 `@/utils/supabase/server` 的 `createClient`。
3. API 请求头是否带 Cookie。

**修复：**

- 确保登录用 `@/utils/supabase/client`。
- API 用 `@/utils/supabase/server`。
- 确认 `middleware.ts` 在跑。

### 11.3 登出后跳转到 `/auth/signout` 空白页

**原因：** `<form>` 缺 `method="post"`，浏览器用 GET 导航。

**修复：**

```tsx
<form action="/auth/signout" method="post">
```

### 11.4 登出后仍显示已登录

**原因：** Server Component 缓存了旧状态。

**修复：**

- 登出后 `router.refresh()`。
- 或用服务端重定向（当前实现已经是）。

### 11.5 `redirect()` 没生效

**原因：** 放在了 `try/catch` 里，被吞掉。

**修复：** `redirect()` 必须在 `try/catch` 外调用。

### 11.6 `cookies() should be awaited`

**原因：** Next.js 15 起 `cookies()` 是异步的。

**修复：**

```ts
const cookieStore = await cookies(); // ✅
const cookieStore = cookies(); // ❌
```

### 11.7 `Email rate limit exceeded`

**原因：** Supabase 免费版对邮件发送频率有限制。

**修复：** 关闭邮箱确认，就不发邮件了。

### 11.8 注册后 `session` 为 null

**原因：** 项目开启了邮箱确认。

**修复：**

- 关闭邮箱确认，或
- 提示用户去邮箱确认。

## 12. 安全注意事项

### 12.1 不要在 Client Component 里调用 `server.ts` 的 client

- `server.ts` 的 `createClient` 依赖 `next/headers`，浏览器里会报错。
- 浏览器端只能用 `client.ts`。

### 12.2 登出必须用 POST

- GET 会被预取、爬虫触发。
- `<form method="post">` 是标配。

### 12.3 不要在 URL 里传敏感信息

- 密码、token 不要放 query string。
- 表单用 POST，body 传。

### 12.4 RLS 是最后一道防线

- 前端鉴权（`getUser`）只影响 UI。
- **真正的数据隔离靠 Supabase RLS**。
- API 里的 `getUser()` 检查是"用户体验优化"，不是安全边界。

### 12.5 Token 不要存 `localStorage`

- `@supabase/ssr` 用 cookie，不用 `localStorage`。
- 如果用原版 `@supabase/supabase-js`，默认存 `localStorage`，**XSS 可窃取**。
- 确认项目用 `createBrowserClient`（来自 `@supabase/ssr`）。

### 12.6 `NEXT_PUBLIC_*` 变量会被打包到客户端

- Publishable Key 是公开的，安全。
- **Secret Key（service_role）绝不能加 `NEXT_PUBLIC_` 前缀**。

### 12.7 生产环境用 HTTPS

- `Secure` cookie 只在 HTTPS 下发送。
- localhost 是例外，浏览器允许 HTTP。
- 部署后确保 HTTPS。

## 13. 总结

认证系统通过**四种角色的分工**实现了完整的登录闭环：

| 角色          | 文件                           | 职责                        |
| ------------- | ------------------------------ | --------------------------- |
| 登录页        | `login/page.tsx`               | 检查登录态，渲染表单        |
| 登录表单      | `login-form.tsx`               | 调 Supabase Auth，写 cookie |
| 登出 API      | `auth/signout/route.ts`        | 清 cookie，重定向           |
| 用户菜单      | `user-menu.tsx`                | 显示状态，触发登出          |
| 浏览器 client | `utils/supabase/client.ts`     | 登录时用                    |
| 服务端 client | `utils/supabase/server.ts`     | 检查 / 登出时用             |
| 中间件 client | `utils/supabase/middleware.ts` | 刷新 token                  |
| 全局中间件    | `middleware.ts`                | 每次请求触发刷新            |

**核心设计原则：**

1. **登录在浏览器**（`createBrowserClient` 自动写 cookie）。
2. **登出在服务端**（`createServerClient` 能清 HttpOnly cookie）。
3. **刷新在中间件**（每次请求触发，用户无感）。
4. **数据隔离靠 RLS**（不是前端检查）。

**关键易错点：**

- `<form>` 必须有 `method="post"`。
- `action` 必须与 `route.ts` 路径一致。
- `cookies()` 必须 `await`。
- `redirect()` 不能放 `try/catch` 里。
- 登录后用 `router.refresh()` 刷新 Server Component。

**目录约定：**

- `/api/*` → 数据接口
- `/auth/*` → 认证流程
- `/login` → 登录页
- `components/auth/*` → 认证组件

按这套结构，未来扩展 OAuth、Magic Link、密码重置时，只需在 `auth/` 下新增 route，在 `login-form.tsx` 里加按钮，无需重构现有代码。
